# AI翻訳の利用上限を順序付き予約で守る

## Status

Accepted

## Context

AI翻訳の月間利用上限（実行回数、文字数、推定費用）とクールダウンは、監査ログ `ai-translation-logs` を集計してから判定していました。集計と予約が分かれているため、同時に届いた複数のリクエストが同じ集計結果を読み、全員が上限内と判定されて AI API を呼べてしまいます。管理画面の翻訳ボタンを続けて押した場合や、複数の編集者が同時に翻訳した場合に、月額費用の上限を超える恐れがありました。

D1 には Payload のデータベースアダプタから使えるトランザクションがなく、判定と予約を 1 つの原子的な操作にまとめられません。また集計は当月分の監査ログを全件読み込んで加算していたため、ログが増えるほど翻訳の開始と管理画面の表示が重くなる構造でした。

検討した選択肢は次のとおりです。

トランザクションで判定と予約を囲む方式は、D1 アダプタがトランザクションを提供していないため採用できません。

月とユーザーの単位で counter 行を持ち、条件付き UPDATE の更新件数で可否を決める方式は原子性を確実に守れます。ただし counter テーブルとマイグレーションが必要になり、監査ログと counter の二重管理になります。実績の訂正や月替わりの取り扱いも増えます。

順序付き予約は、判定より先に予約行を作り、自分の予約より前の予約だけを数えて判定する方式です。既存の監査ログだけで成立し、新しいテーブルもマイグレーションも要りません。

## Decision

- AI 翻訳の実行は、上限判定より先に `status: pending` の予約行を監査ログへ挿入する。予約行には今回の文字数と見込み費用を入れる
- 集計では「当月の succeeded と failed のすべて」と「自分の予約 id より小さい pending」だけを数える。SQLite の id は挿入順に増え、同一データベースへの書き込みは直列化されるため、id が小さい予約は必ず先に確定している
- 上限に達していた場合は、自分の予約行を `rejected`（見込み費用は 0）へ確定してから拒否する
- クールダウンも同じ順序で判定する。同一ユーザー、同一ドキュメント、同一言語について、自分の予約より前の直近実行だけを見る
- 予約行を作れなかった場合は AI API を呼ばずに中止する。予約のない実行は集計から漏れ、上限をすり抜けるため
- 当月の集計は監査ログの全件読み込みをやめ、件数と文字数と費用を 1 回の SQL 集約で求める。集計できなかった場合は 0 とみなさず拒否する
- 異常終了などで確定しなかった予約は、翻訳の実行時に 10 分で失効させ `failed` へ回収する。API を呼んだ後に落ちた可能性があるため、費用は見込み額のまま実費として数える

## Consequences

- 同時に何件届いても、上限を超えて AI API が呼ばれることはなくなる。同時実行のテストでは、残枠が 1 件のとき成功はちょうど 1 件になる
- 拒否された予約が `rejected` へ確定するまでの短い間は、後続がその予約を数えてしまう。このため本来通せた実行が拒否されることはありうる。上限を守る側に倒した設計として受け入れる。利用者は再実行すれば通る
- 監査ログには実行中の予約が見えるようになる。失効した予約は失敗として残り、実行中のまま残り続けることはない
- 当月の集計はログ件数に比例した読み込みをしなくなり、翻訳の開始と管理画面の利用状況パネルが軽くなる
- 集計結果を返せないときは翻訳を止める。上限の判定材料がないまま API を呼ぶよりも安全側に倒している
- 判定は id が挿入順に増えることに依存する。`ai_translation_logs` は AUTOINCREMENT ではないため、最大 id の行を削除すると id が再利用されうる。監査ログはどのロールにも削除を許可しておらず、この前提を崩す行の削除や間引きを追加する場合はこの決定を見直す
