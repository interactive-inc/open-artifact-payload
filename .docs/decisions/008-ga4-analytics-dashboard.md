# 管理画面のダッシュボードでGA4のアクセス解析を見せる

## Status

Accepted

## Context

案件のサイトは計測タグ（サイト設定の GA4 タグ ID / GTM ID）を埋め込めますが、計測した結果は GA4 の画面へ移らないと見られません。運用者が毎日管理画面を開いたときに、アクセスの増減・よく読まれたページ・流入元・問い合わせ件数をまとめて確認できるようにします。

レポートの文章生成は CMS に組み込みません。分析と文章化は、利用者が手元の AI サブスクリプションと MCP で行うほうが安く、CMS には数字とグラフの表示だけを持たせます。

テンプレートの機能として、クライアント案件でも同じ手順で導入できることを前提にします。GA4 プロパティは実装会社のアカウントにある場合も、クライアントのアカウントにある場合もあります。

検討した取得方式は次のとおりです。

表示時に取得して一時保存する方式は、ダッシュボードを開いたときに GA4 Data API へ問い合わせ、結果を一定時間使い回します。定期実行が不要で、案件側の `wrangler.jsonc` や `cloudflare-worker.ts` に手を入れずに機能フラグだけで動きます。

毎朝の定期実行で取得して保存する方式は、表示が常に速く GA4 の障害時も前回の値を出せます。ただし案件ごとに Cron Triggers と `scheduled` ハンドラを足す必要があり、テンプレート機能としての導入手順が重くなります。GA4 自体が過去データを保持しているため、自前で履歴を積み上げる利点も小さいです。

Looker Studio の埋め込みはコードがほぼ不要ですが、閲覧者全員に Google アカウントの権限が必要になります。権限を省くと公開リンクになり、ロールでの絞り込みもできません。

## Decision

### 取得方式と機能フラグ

- 表示時に取得して一時保存する方式を採る
- `ProjectFeatures` に `enableAnalytics` を追加する。false の案件では設定 Global・一時保存・ダッシュボードのパネルがすべて登録されない
- ダッシュボードは設定 Global `analytics-settings` が登録されているかで機能の有無を判定する。core から案件の機能フラグの値を直接 import しない
- 新しい REST エンドポイントは作らない。ダッシュボードはサーバーコンポーネントで描画し、GA4 への問い合わせもサーバー内で完結させる。期間の切り替えは `/admin?range=7d` のような URL パラメータで再描画する
- 新しい依存パッケージは入れない。認証は Web Crypto で RS256 の JWT を署名し、グラフは既存の `recharts` を使う

### 認証と鍵

- サービスアカウントはサイトごとに分ける。各サービスアカウントは対象サイトの GA4 プロパティにだけ「閲覧者」で追加する。1 サイトの鍵が漏れても読めるのはそのサイトの数字だけで、共通アカウントで起きうる「プロパティ ID を書き換えて他案件のデータを読む」ことが構造的に起きない
- 鍵の JSON は環境変数 `GA4_SERVICE_ACCOUNT_JSON` でのみ扱う。本番は `wrangler secret`、ローカルは `.env`。DB に保存せず、画面にもブラウザにも送らない。設定画面に出すのは設定済みかどうかだけ
- GA4 への問い合わせのたびに `analytics.readonly` スコープのアクセストークンを `https://oauth2.googleapis.com/token` から取得する。呼び出しは 1 日に数回なのでトークンは保存しない
- `GA4_SERVICE_ACCOUNT_JSON` をデプロイ前検査の任意 secret に加える

### 設定 Global

- slug は `analytics-settings`、ラベルは「アクセス解析設定」、グループは「システム」
- 閲覧と更新は admin 以上（`isAdminOrServiceAdmin`）。editor には管理画面のナビにも出さない
- 接続状態（UI フィールド）は、鍵が設定済みか、プロパティ ID が入力済みか、最後に取得した日時、直近のエラーの要約を表示する
- GA4 プロパティ ID は数字だけを受け付ける（共有 validator `validateGa4PropertyId`）。導入時に実装会社が設定する項目のため、更新は serviceAdmin に限る
- 見られるロールは「管理者」「編集者」の複数選択で、既定は管理者だけ。serviceAdmin は選択に関係なく常に閲覧できる。何も選ばなければ serviceAdmin だけが見られる。admin 以上が変更できる
- 人単位の指定は持たない

### 取得するデータ

- GA4 Data API の `batchRunReports` で 4 種類の集計を 1 回の HTTP 呼び出しにまとめる
- アクセス推移は `date` ごとの `activeUsers` と `screenPageViews`。GA4 は値が 0 の日を返さないため、表示側で欠けた日を 0 で補う
- 前の期間との比較は、次元なしで 2 つの期間（今の期間とその直前の同じ長さの期間）を指定し、`activeUsers`・`screenPageViews`・`sessions` の合計を取る。行は自動で付く `dateRange` 次元の `date_range_0` / `date_range_1` で見分ける
- 人気ページは `pagePath` ごとの `screenPageViews` の上位 10 件。`pagePath` はクエリ文字列を含まないため、URL に入った個人情報を表示しない
- 流入元は `sessionDefaultChannelGroup` ごとの `sessions`。表示名は日本語に置き換え、未知の分類は GA4 の名前のまま出す
- 期間は 7 日・28 日・90 日。初期値は 28 日。終わりは日本時間の昨日で、開始日と終了日は日付文字列で明示して送る。今日の分は集計途中で少なく見えるため含めない。GA4 はプロパティのタイムゾーンで日付を区切るため、日本の案件では同じ日付になる
- 問い合わせ件数は `contact-submissions` の作成日時を日本時間の日ごとに数える。GA4 の設定が無い案件でも表示できる。表示するのは件数だけで、問い合わせの内容は読まない

### 一時保存

- Payload 標準の KV（既存の `payload_kv` テーブル）に、期間ごとのキー `analytics:traffic:<期間>` で GA4 の結果を保存する。新しいテーブルは作らない
- 保存から 3 時間以内ならそれを使い、超えていれば取得し直す。呼び出しは期間ごとに 1 日 8 回が上限で、GA4 の無料枠に対して十分に小さい
- 読み出した値は Zod で形を確かめ、合わなければ保存が無いものとして扱う
- 同時に開いた 2 人が両方取得しても結果を上書きするだけなので、排他制御は入れない
- 取得の成否はキー `analytics:status` に記録し、設定画面の接続状態に出す
- 問い合わせ件数は保存せず、表示のたびに数える

### 失敗時の表示

- 機能フラグがオフ、または見られないロールのときはパネルを出さず、GA4 にも問い合わせない
- 鍵かプロパティ ID が無いときは、問い合わせ件数だけを出し、GA4 の部分に「未接続です」と表示する。admin 以上には設定画面へのリンクも出す
- 取得に失敗して前回の保存がある場合は、前回の結果に「最新の取得に失敗しました（前回取得: 時刻）」と添えて出す
- 取得に失敗して前回の保存も無い場合は、原因に応じた対処を表示する。401・403 は権限不足として GA4 への追加の確認を促す。429 は時間をおいて開き直すよう促す。10 秒の打ち切り・5xx・通信失敗は GA4 から応答が無いと表示する。鍵の形式やトークン交換の失敗は鍵の設定を確認するよう促す
- GA4 の応答は Zod で形を確かめてから保存する。想定外の形は失敗として扱う
- 鍵の中身・アクセストークン・GA4 の応答本文はログにもエラー表示にも載せない
- 前の期間が 0 のときは増減を「—」で表示する。不正な期間パラメータは 28 日として扱う

### 画面

- パネルはダッシュボードのタスクカードの下、最近の更新の上に置く。今の「何をしますか」の流れを崩さない
- 中身は、数字 4 つ（ユーザー・表示回数・セッション・問い合わせと前の期間からの増減）、日ごとの推移の折れ線（実線が今の期間、点線が前の期間）、人気ページ上位 10 件、流入元の横棒の順に並べる
- 右上に 7 日 / 28 日 / 90 日の切り替え、下に「昨日までの N 日間・取得時刻」を表示する
- パネルは Suspense で分け、GA4 の応答を待つ間もタスクカードと最近の更新を先に表示する
- グラフには数値を読み上げられる代替を付ける

## Consequences

- 案件は `src/cms/project-features.ts` に `enableAnalytics` を足し、サービスアカウントの鍵と GA4 プロパティ ID を設定するだけで使える。案件側の Worker 設定は変わらない
- その日最初にダッシュボードを開いた人だけ、GA4 の応答を待つ 1〜2 秒ほどパネルの表示が遅れる
- 毎朝のメール配信など定期処理が必要になったら、同じ取得処理を Cron Triggers から呼べば定期取得方式へ広げられる
- サイトごとのサービスアカウントの作成と GA4 への追加が導入作業として残る。GA4 がクライアントのアカウントにある場合は、クライアントに閲覧者の追加を依頼する。クライアントはいつでも GA4 側でアカウントを外して止められる
- 組織のポリシーでサービスアカウント鍵の作成が禁止されている場合、この方式は使えない。その場合は認証部分だけを別の方式に差し替える
- GA4 の数字は処理に最大 48 時間ほどかかるため、昨日の値は後から少し増えることがある
